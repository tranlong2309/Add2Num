# Business Requirements Analysis: Work Order Management

## Source Requirement

The Product Owner described an urgent POSCO MCI feature for technicians working at construction sites. A technician enters an active equipment identifier, selects one priority from `low`, `medium`, `high`, or `urgent`, and writes a work description. The system stores the work order and shows a list for a supervisor. The feature is requested within one week. The Product Owner stated that complex authorization is not required because every logged-in construction-site user is a technician, provided that the equipment identifier is valid and active.

## 1. Entities and Basic Attributes

### WorkOrder

| Attribute     | Type       | Required | Initial interpretation                                           |
| ------------- | ---------- | -------: | ---------------------------------------------------------------- |
| `id`          | Identifier |      Yes | System-generated work order identifier.                          |
| `equipmentId` | String     |      Yes | Identifier of an active equipment item.                          |
| `description` | String     |      Yes | Technician's description of the work.                            |
| `priority`    | Enum       |      Yes | One of `low`, `medium`, `high`, or `urgent`.                     |
| `status`      | Enum       |      Yes | Initial state is likely `NEW`; the lifecycle needs confirmation. |
| `createdAt`   | Date-time  |      Yes | Creation timestamp generated by the server.                      |
| `createdBy`   | Identifier |      Yes | Authenticated technician identity.                               |

### Equipment

| Attribute | Type    | Required | Initial interpretation                                       |
| --------- | ------- | -------: | ------------------------------------------------------------ |
| `id`      | String  |      Yes | Equipment identifier entered by the technician.              |
| `active`  | Boolean |      Yes | Determines whether a work order may reference the equipment. |

### User

| Attribute | Type       | Required | Initial interpretation                                                |
| --------- | ---------- | -------: | --------------------------------------------------------------------- |
| `id`      | Identifier |      Yes | Authenticated user identifier.                                        |
| `role`    | Enum       |      Yes | At minimum, technician and supervisor behavior must be distinguished. |

## 2. Open Questions and Business Risks

1. Which authentication provider and token format identify a logged-in construction-site user?
2. Does every authenticated user have technician permissions, or must the system still verify a technician role?
3. Which users may view the work-order list: one supervisor, all supervisors, or all authenticated users?
4. Is `equipmentId` case-sensitive, and what exact format and maximum length are valid?
5. What is the authoritative source for equipment status, and how quickly must an inactive equipment change be reflected?
6. What is the minimum and maximum length of `description`?
7. Should whitespace-only descriptions be rejected, and should descriptions allow markup or line breaks?
8. What is the default status and what state transitions are allowed after creation?
9. Can a technician create duplicate work orders for the same equipment and description?
10. Which time zone and clock source define `createdAt`?
11. What should the API return when the equipment does not exist or is inactive?
12. Are priority values case-sensitive, and should invalid values return a validation error or be normalized?
13. What offline or retry behavior is required for the mobile application?
14. What retention, audit, export, and deletion rules apply to work orders?
15. What response-time and expected-volume targets apply to the one-week release?
16. Which security and privacy requirements apply to work descriptions and technician identity?

## 3. UI / Data / API Decomposition

| Layer | Create Work Order                                                                                                                                                                                 | View Work-Order List                                                                                                                           |
| ----- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| UI    | Equipment identifier input, priority selector, description input, validation messages, submit action, offline or retry state if required.                                                         | Supervisor list, filtering and sorting requirements, status and priority display, loading state, empty state, and error state.                 |
| Data  | `WorkOrder` record, equipment reference, priority enum, status enum, creator identity, server timestamps, validation constraints, and audit fields.                                               | Query model for work orders, pagination strategy, filters, sort order, authorization scope, and consistent timestamps.                         |
| API   | `POST /api/work-orders` with the explicitly approved request fields. Validate equipment existence and active status before persistence. Return a documented success response and RFC 7807 errors. | `GET /api/work-orders` with explicitly approved query parameters. Enforce supervisor access rules and return a documented collection response. |

## Assumptions Requiring Confirmation

This analysis deliberately does not finalize authorization, status transitions, field lengths, response schemas, persistence technology, or offline behavior. These are decision points for the Product Owner and technical stakeholders, not implementation assumptions.

## Add2Num Applicability

The current Add2Num project is a large-number addition application and has no Work Order entities, authentication, database, or mobile UI. This document satisfies the lab's analysis exercise as a standalone business-analysis artefact. Implementing the Work Order feature would require a separate approved scope and architecture decision.
